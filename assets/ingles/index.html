Definition · What the system does

Functional Requirements Definition

“

A functional requirement describes a behavior or service the system must provide: what it does, for whom, and under which conditions.

  • Describes behavior: inputs, processing and outputs.
  • Written from the user’s or the business’s point of view.
  • Specific and testable: start with “The system shall…”.
  • Becomes the base for design, code and test cases.
Behavior, not quality

Example

“The system shall email a booking confirmation within 30 seconds of payment.”

Tip

If you cannot write a test for it, the requirement is still too vague.

Types · The functional family

Functional Requirements Types

One family, six lenses

Same family, different lenses

Most functional requirements fit one of these groups. The group tells you who cares about it and how to test it.

These are lenses, not boxes: one requirement can be a user requirement and a system requirement at the same time.

User System Data Rules Reports Integration

User requirements

What users need to achieve with the product.

e.g. Sign in with a Google account.

System requirements

Detailed behavior the software must execute.

e.g. Validate the email format before saving.

Data & CRUD

Create, read, update and delete records.

e.g. Edit a customer profile.

Business rules

Policies that constrain what the system allows.

e.g. Only admins can delete accounts.

Reporting

Summaries, dashboards and exports.

e.g. Monthly sales report in PDF.

Integration

Connections with external systems or APIs.

e.g. Sync orders with the payment gateway.

Definition · How well it works

Non-Functional Requirements Definition

“

A non-functional requirement describes how well the system must perform: its quality attributes and constraints, not its features.

  • Describes quality, not behavior.
  • Usually applies to the whole system.
  • Must be measurable: numbers, not adjectives.
  • Shapes user trust, cost and architecture.
Quality you can measure

Example

“95% of requests must respond in under 2 seconds with 1,000 concurrent users.”

Tip

“Fast” is not a requirement. “Under 2 s at 1,000 users” is.

Types · The quality family

Non-Functional Requirements Types

Six qualities that make it good

A system can do everything right and still be slow, unsafe or impossible to maintain. These attributes decide whether it is actually usable.

Every NFR needs a metric, a target and a way to verify it. Otherwise it is just a wish.

Quality attributes

Performance

Speed and throughput under real load.

e.g. Page response under 2 s.

Scalability

Grows with users, data and traffic.

e.g. Support 10,000 concurrent users.

Reliability & availability

Uptime and recovery from failure.

e.g. 99.9% uptime and daily backups.

Security

Protects data, access and privacy.

e.g. Encryption at rest and MFA.

Usability & accessibility

Easy for everyone, on any device.

e.g. WCAG 2.1 AA compliance.

Maintainability

Easy to change, test and fix.

e.g. 80% automated test coverage.

Side by side

Functional vs. non-functional

Same system, two different questions. If you can swap “how well” for a number, you are probably looking at an NFR.

Aspect Functional Non-functional
Question answered What does the system do? How well does it do it?
Focus Behavior and features Quality and constraints
Scope A specific function The whole system
Example “The app sends a confirmation email.” “The email arrives in under 5 seconds.”
How to verify Functional tests and acceptance criteria Benchmarks, load tests and audits
